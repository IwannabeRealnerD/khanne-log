# E2E 테스트 계획 생성 커맨드

사용자의 요청을 분석하여 프로젝트 루트의 `tmp/blueprints/YYYY-MM-DD/` 디렉토리에 E2E 테스트 계획 파일을 생성하고, 파일 기반으로 대화합니다.

## 핵심 원칙

**1. `.md` 파일이 대화의 중심이다.**

- 질문이 있으면 파일에 작성
- 사용자가 파일에서 답변
- 답변이 반영되면 `## 결정 사항` 섹션으로 변환하여 맥락 보존

**2. 애매하면 질문부터.**

- 사용자가 "실행해"라고 해도 계획이 애매하면 추가 질문
- 질문은 `.md` 파일에 작성
- LLM이 자신있게 구현할 수 있는 수준이면 실행
- 판단하기에 명확하지 않은 질문이나 요청이면 광범위한 코드베이스 탐색을 하지 말고, 더 정확한 프롬프트를 제공하도록 유도한다

**3. 탐색 전 확인. 단, MCP와 코드베이스로 알 수 있는 건 직접 탐색.**

- 코드베이스를 광범위하게 탐색하기 전에 어떤 특정 영역이나 파일에 집중할지 물어본다
- 명시적으로 요청하지 않는 한 자율적인 광범위 코드베이스 탐색을 하지 않는다
- 단, Playwright MCP로 화면 구조를 파악하거나 코드베이스에서 라우트·미들웨어·기존 테스트를 확인하는 것은 직접 수행한다. 사용자에게 물어볼 필요 없이 해결 가능한 건 스스로 해결

**4. 계획 파일은 자기완결적이어야 한다.**

- 계획 파일만 읽으면 **새 세션에서도 실행 가능**해야 한다
- **인라인 기록** (세션 간 유실되는 정보): 결정 사항, 대상 파일 경로, API 엔드포인트·응답 형태, 유사 구현 참조 경로, 비즈니스 맥락
- **참조만** (새 세션에서도 로드 가능): 스킬 규칙(이름만 명시), AGENTS.md 내용, 코드 구현 상세(파일에 이미 존재)
- 각 Step에 `**맥락**` 필드를 작성하여 해당 Step 실행에 필요한 최소 배경 정보를 기록한다
- **실행 방식도 계획 파일에 명시**: Step이 2개 이상이면 `## 실행 방식` 섹션에 서브에이전트 위임 프롬프트 템플릿(계획 파일 절대 경로, 프로젝트 루트 절대 경로 포함)과 주의사항을 기록한다. 새 세션에서 계획 파일만 보고도 실행 방법을 알 수 있어야 한다

**5. 이상 감지 시 즉시 중단하고 사용자에게 알린다.**

모든 Phase에서 "말이 안 되는 상황"을 감지하면 **무리하게 진행하지 않고 즉시 멈춘다**. 중단 시에는 현재 상태, 발견한 이상, 왜 진행이 불가능한지를 명확히 보고한다.

**중단 조건 (Stop Conditions):**

| 카테고리        | 구체적 상황                                     | 먼저 시도                                                          | 그래도 안 되면                          |
| --------------- | ----------------------------------------------- | ------------------------------------------------------------------ | --------------------------------------- |
| **환경 이상**   | dev 서버 미기동, MCP 연결 실패, 타임아웃        | 서버 재실행, `browser_install`                                     | 에러 로그와 함께 중단 보고              |
| **UI 불일치**   | 예상 요소 없음, 다른 화면, 요소 disabled/hidden | `browser_snapshot`으로 현재 상태 재확인, `browser_wait_for`로 대기 | 스냅샷 결과 공유 후 중단 보고           |
| **인증/권한**   | 로그인 후에도 접근 불가, 권한 부족              | 로그인 흐름 재수행                                                 | 인증 상태 보고 후 중단 보고             |
| **데이터 부재** | 테스트 데이터 없어 시나리오 진행 불가           | —                                                                  | 필요한 데이터 조건 명시 후 중단 보고    |
| **논리 모순**   | 시나리오 흐름 ≠ 실제 앱 동작, 계획과 현실 괴리  | —                                                                  | 계획 vs 실제 차이점 보고 후 중단 보고   |
| **반복 실패**   | 동일 작업 3회 실패, 원인 파악 불가              | —                                                                  | 시도 내역과 에러 로그 공유 후 중단 보고 |

**중단 보고 형식:**

```
🛑 [Phase/Step 번호] 작업 중단

**상황**: (현재 무엇을 하고 있었는지)
**이상 내용**: (무엇이 예상과 다른지)
**시도한 것**: (해결을 위해 시도한 내용, 있다면)
**판단**: (왜 계속 진행하면 안 되는지)
**필요한 조치**: (사용자가 해결해야 할 것)
```

## 실행 플로우

### Phase 0: 로컬 dev 서버 확인

E2E blueprint는 로컬 개발환경에서 실행됩니다. MCP 탐색 전에 대상 앱의 dev 서버가 실행 중인지 확인하고, 꺼져 있으면 실행합니다.

1. 대상 앱의 dev 서버 포트로 접속 가능한지 확인 (`curl -s -o /dev/null -w "%{http_code}" http://localhost:<포트>`)
2. 접속 불가 시, 해당 앱의 dev 서버를 백그라운드로 실행 (`pnpm <앱-alias> dev`)
3. 서버가 준비될 때까지 대기 후 Phase 1 진행
4. **중단 조건**: 서버 실행 후 30초 내 접속 불가, 빌드 에러 발생 시 → 에러 로그와 함께 사용자에게 보고 후 중단

**앱별 dev 서버 포트** (각 앱의 `package.json`의 `dev` 스크립트 참조):

| 앱               | alias              | 포트 |
| ---------------- | ------------------ | ---- |
| Dashboard        | `dashboard`        | 3003 |
| KYC              | `kyc`              | 3005 |
| Remittance Admin | `remittance-admin` | 3009 |

> 위 목록에 없는 앱은 해당 앱의 `package.json`에서 `-p` 옵션을 확인합니다.

### 1. 파일 확인 및 재개 판단

- 기존 계획 파일이 있는지 확인 (`tmp/blueprints/` 디렉토리)
- **기존 파일이 있으면**: 파일을 읽고 상태를 파싱하여 재개 지점을 결정
  - `## 질문` 섹션이 있고 답변이 채워져 있으면 → Step 3으로 진행 (답변 기반 계획 작성)
  - `## 질문` 섹션이 있고 답변이 비어 있으면 → 사용자에게 답변 요청하고 대기
  - `## 진행 상황`의 Step 체크박스를 파싱: `[x]` 완료 건너뜀, `[~]` 진행중이면 해당 Step부터 재개
  - 모든 Step이 `[ ]`이면 처음부터 시작
- **없으면**: 새 파일 생성

### 2. 명확성 검증 및 질문

계획을 작성하기 전에 다음이 명확한지 확인:

- **목표**: 어떤 E2E 테스트를 작성하려는 건지?
- **범위**: 어느 앱의 어떤 페이지/흐름을 테스트할 건지?
- **제약조건**: 인증 필요 여부, 테스트 데이터 조건 등
- **우선순위**: 여러 시나리오가 있다면 뭐부터?

**불명확한 경우** → 파일에 `## 질문` 섹션을 추가하고 사용자에게 답변을 요청한다. 답변은 각 질문 바로 아래에 인라인으로 작성하도록 안내한다. 체크박스는 에이전트가 처리하므로 사용자는 답변만 작성하면 된다:

```markdown
# 계획 제목

## 질문

아래 질문에 답변해주세요. 각 질문 바로 아래 `> 답변:` 뒤에 답변을 작성한 후 `/e2e-blueprint-skill`을 다시 호출하세요.

- [ ] 질문 1?
  > 답변:
- [ ] 질문 2?
  > 답변:
```

사용자에게 파일 경로를 안내하고 대기.

**명확한 경우 (또는 답변 확인 후)** → 답변이 있으면 `## 질문` 섹션을 `## 결정 사항` 섹션으로 변환하여 맥락을 보존한다:

```markdown
## 결정 사항

- 테스트 대상: Dashboard 로그인 흐름
- 인증 방식: 이메일/비밀번호 로그인 후 대시보드 리다이렉트 확인
```

그 후 Step 3으로 진행.

### 3. 계획 작성 (서브에이전트)

목표·범위가 확정되면, **서브에이전트에 계획 작성을 위임**한다. 메인 에이전트는 질문/답변 과정에서 축적된 컨텍스트를 정리하여 서브에이전트에 전달하고, 서브에이전트가 MCP 탐색·스킬 탐색부터 계획 파일 작성까지 수행한다.

**메인 에이전트가 전달할 정보:**

- 사용자의 원래 요청
- 결정 사항 (질문/답변 과정에서 확정된 내용)
- 추가 요청 사항 (사용자가 구현 시 반영해야 할 사항)
- 계획 파일 경로 (날짜 디렉토리 + 파일명)
- 프로젝트 루트 절대 경로
- 대상 앱의 dev 서버 URL

**계획 작성 서브에이전트 프롬프트 템플릿:** `prompts/plan-writer.md`를 읽어서 `{변수}`를 치환한 뒤 서브에이전트에 전달한다.

> Step 구성 예시와 시나리오 작성 원칙은 `./templates/blueprint-templates.md`의 해당 섹션을 참조한다.
> 구현 실행 시, 각 Step 진입 전에 해당 Step의 `참조 스킬`을 호출하여 규칙을 로드한 뒤 작업한다.

서브에이전트가 계획 파일 작성을 완료하면, 메인 에이전트는 결과를 확인하고 다음 단계(계획 검증)로 진행한다.

### 4. 계획 검증 (서브에이전트)

계획 파일 작성이 완료되면 **서브에이전트를 사용하여 계획 자체를 검증**한다. 실행 결과가 아닌 **플랜의 품질**을 검토하는 단계이다.

**검증 항목:**

1. **논리적 정합성**: Step 간 순서가 맞는지, 의존 관계가 올바른지, 누락된 단계가 없는지, 시나리오 목록과 실제 Step 작업 내용이 일치하는지
2. **사용자 의도 반영**: 사용자가 요청한 목표·범위·제약조건이 계획에 정확히 반영되었는지, 결정 사항이 왜곡 없이 기록되었는지

**절차:**

1. 계획 파일 작성 완료 후, Agent 도구(`subagent_type: "general-purpose"`)로 검증 서브에이전트를 생성
2. 서브에이전트가 계획 파일을 읽고 검증 수행
3. 검증 결과를 메인 에이전트가 받아서 사용자에게 보고
4. **문제가 발견되면**: 사용자에게 검증 결과를 공유하고, 수정이 필요한 부분을 계획 파일에 반영한 뒤 재검증 여부를 확인
5. **문제가 없으면**: 검증 통과를 알리고 다음 단계(구현 실행)로 진행

**검증 서브에이전트 프롬프트 템플릿:** `prompts/plan-validator.md`를 읽어서 `{변수}`를 치환한 뒤 서브에이전트에 전달한다.

> **주의**: 검증은 계획의 구조와 논리만 검토한다. 코드베이스 탐색이나 실제 구현 가능성 검증은 이 단계에서 수행하지 않는다.

### 5. 구현 실행

Step이 2개 이상인 계획은 반드시 서브에이전트를 사용한다. Step이 1개뿐인 단순 작업은 메인 에이전트가 직접 실행해도 된다.

사용자가 "실행해"라고 하면 **메인 에이전트는 오케스트레이터 역할**을 하며, 계획 파일의 `## 실행 방식` 섹션에 명시된 위임 프롬프트와 주의사항에 따라 각 Step을 `e2e-writer` 에이전트에 위임한다. (`./templates/blueprint-templates.md`의 `## 실행 방식` 참조)

**e2e-writer 시스템 프롬프트:** `prompts/e2e-writer.md`를 읽어서 서브에이전트에 전달한다.

**구현 완료 후 검증:**

모든 Step이 완료되면 다음 두 단계를 순차적으로 실행한다.

#### 5-1. e2e-skill 준수 검증

`feature-dev:code-reviewer` 서브에이전트에 위임하여, 작성된 E2E 테스트 코드가 e2e-skill 규칙을 준수하는지 검증한다. 스킬 파일 경로(`{프로젝트 루트}/.Codex/skills/e2e-skill/SKILL.md`)와 테스트 파일 경로를 전달하고, import 패턴·Locator 우선순위·테스트 격리·Assertion·파일 구조를 중점 확인하도록 한다. 위반 사항이 발견되면 수정 후 재검증.

#### 5-2. E2E 테스트 실행

```bash
pnpm --filter e2e e2e:test -- {작성된 테스트 파일 경로}
```

- **실패 시**: 에러 로그 분석 → 코드 수정 → 재실행 (최대 3회). 3회 실패 시 원인을 `## 고려사항`에 기록하고 **중단 보고 형식에 따라 사용자에게 보고 후 중단**.
- **성공 시**: `## 진행 상황`에서 검증 단계를 `[x]`로 업데이트.

### 6. 파일 경로 안내

생성/업데이트된 파일 경로를 사용자에게 알려줌.

## 파일 규칙

- **위치**: 항상 **git 루트 디렉토리**의 `tmp/blueprints/YYYY-MM-DD/`에 생성 (예: `platform-frontend/tmp/blueprints/2026-02-28/`)
  - 절대로 하위 앱 폴더(apps/xxx/)에 생성하지 않음
  - monorepo인 경우에도 최상위 루트에 생성
- **디렉토리 구조**: `tmp/blueprints/YYYY-MM-DD/N-짧은-계획-제목.md` (날짜 디렉토리 + incremental 번호 prefix + 영문 kebab-case 파일명)
  - `N`은 해당 날짜 디렉토리 내 기존 파일 수를 기준으로 자동 증가 (1, 2, 3, ...)
  - 예: `1-dashboard-login-e2e.md`, `2-kyc-flow-e2e.md`
- **디렉토리 없으면 생성**

## Playwright MCP 도구 용도

| 도구                      | 용도                             | 사용 시점                                         |
| ------------------------- | -------------------------------- | ------------------------------------------------- |
| `browser_navigate`        | 특정 URL로 이동                  | 대상 페이지 최초 접속, 페이지 간 이동 확인        |
| `browser_snapshot`        | 현재 페이지의 접근성 스냅샷 조회 | 페이지 구조·요소 파악, 텍스트·역할 확인           |
| `browser_click`           | 요소 클릭                        | 네비게이션 링크, 버튼 등 클릭하여 흐름 탐색       |
| `browser_fill_form`       | 폼 필드에 값 입력                | 로그인 폼, 검색 폼 등 입력 흐름 확인              |
| `browser_select_option`   | 드롭다운/셀렉트 옵션 선택        | 드롭다운 메뉴, 셀렉트 박스 등 옵션 선택 흐름 확인 |
| `browser_wait_for`        | 특정 조건까지 대기               | 페이지 로딩, 리다이렉트 완료 대기                 |
| `browser_take_screenshot` | 화면 스크린샷 캡처               | 시각적 레이아웃 확인, 디버깅                      |

### MCP 탐색 팁

- **snapshot 먼저**: 페이지 접속 후 `browser_snapshot`으로 전체 구조를 파악한 뒤 인터랙션 진행
- **리다이렉트 확인**: `browser_navigate` 후 실제 URL이 예상과 다르면 리다이렉트 로직 존재
- **인증 필요 페이지**: 로그인 없이 접근 시 리다이렉트되는지 확인하여 인증 흐름 파악
