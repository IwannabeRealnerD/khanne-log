# 마크다운 문서화 가이드

`docs/` 디렉토리에서 **특이사항만** 마크다운으로 관리합니다.

## 핵심 원칙

- **배치 확인 필수**: 문서를 새로 생성하거나 기존 문서를 대폭 보강할 때, 작업 전에 반드시 사용자에게 **어디에 넣을지** 확인한다. `domains/`와 `apps/` 중 어디가 적절한지, 기존 문서에 통합할지 새 파일로 만들지를 물어본 뒤 진행한다.
- **코드 우선**: 컴포넌트 구조, 상태 관리, 구현 패턴은 코드로 관리
- **특이사항 중심**: 에러 케이스, 비즈니스 로직 예외, 주의사항, edge cases만 문서화
- **Colocation**: 페이지/기능 관련 문서는 해당 디렉토리 내부에 배치

## 기본 디렉토리 구조

**Colocation 원칙에 따라 문서는 해당 기능이 있는 디렉토리 계층과 동일하게 배치합니다.**

```
docs/
├── domains/                     # 백엔드 서비스/도메인 기준 문서
│   └── [service-name]/          # 백엔드 서비스별 (예: remittance, local-kr)
│       └── [domain]/            # 도메인별 폴더 (예: transfer, balance, kyc)
│           ├── _overview.md     # 도메인 개요 + 세부 문서 링크 (인덱스 역할)
│           └── [topic].md       # 세부 주제별 문서
│
├── apps/                        # 프론트엔드 앱 기준 문서
│   └── [app-name]/              # 앱별 (예: dashboard, remittance-admin)
│       └── [feature]/           # 기능별 폴더 (예: balance, transfer)
│           ├── _overview.md     # 기능 개요 + 세부 문서 링크 (인덱스 역할)
│           └── [topic].md       # 세부 주제별 문서
│
├── _plan.md                     # 구현 계획
└── _todo.md                     # 할일 추적
```

### 문서 작성 규칙

**domains/ 문서** (백엔드 서비스/도메인 기준):

- 토픽 문서: `docs/domains/[service-name]/[domain]/[topic].md`
- 도메인 개요: `docs/domains/[service-name]/[domain]/_overview.md`
- 해당 도메인 전체에 적용되는 특이사항, 주의사항 기록

**apps/ 문서** (프론트엔드 앱/기능 기준):

- 토픽 문서: `docs/apps/[app-name]/[feature]/[topic].md`
- 기능 개요: `docs/apps/[app-name]/[feature]/_overview.md`
- 작성 기준은 domains/와 동일 (특이사항 중심)

**`_overview.md` 역할:**

- 도메인/기능의 **인덱스 페이지** 역할 (개요 + 세부 문서 링크)
- 전체에 걸쳐 적용되는 특이사항을 상단에 기록
- `## 세부 문서` 섹션에서 해당 디렉토리 내 토픽 문서들을 링크
- **새 토픽 문서를 추가할 때 반드시 `_overview.md`의 세부 문서 목록에도 링크를 추가**한다

**예시:**

- `docs/domains/remittance/transfer/_overview.md` - 송금 도메인 개요 + 세부 문서 링크
- `docs/domains/remittance/transfer/master-transfer-status.md` - 모송금 상태 관련 특이사항
- `docs/domains/local-kr/kyc/_overview.md` - KYC 도메인 개요
- `docs/domains/local-kr/kyc/force-kyc.md` - 강제 KYC 관련 특이사항
- `docs/apps/dashboard/balance/_overview.md` - 대시보드 잔고 기능 개요

## 작성 내용

**다음만 작성:**

- 비직관적인 비즈니스 로직
- 예상치 못한 에러 케이스 및 처리 방식
- 성능상 주의사항
- 외부 서비스/API 의존성
- 팀에서 합의한 특별한 규칙

### 작성 대상 ✅

- **API 응답 처리**: 배열 응답인데 첫 번째 요소만 사용하는 경우 등
- **미사용 필드**: 존재하지만 현재 미사용(향후 확장용)인 필드
- **제약사항**: 특정 상태에서만 동작하는 제약
- **에러 처리**: 일반적이지 않은 fallback·재시도 등
- **하드코딩된 값**: 매직 넘버, 설정 변경 불가인 값

### 작성 제외 ❌

- 컴포넌트 구조, 상태 관리 패턴 (코드 참조)
- 일반적인 기능 설명, 자명한 구현 로직
- 표준 디자인 패턴

## 코드 기반 특이사항 추출 규칙

코드를 분석하여 문서를 작성할 때는 **특이사항만** 추출하여 작성합니다.

### 1. 코드 주석 참조

관련 기능의 코드 주석을 확인하고, 일반적인 동작 설명이 아닌 **특이사항/주의사항만** 문서에 반영합니다.

**작성 대상 예시:**

```typescript
// ✅ 문서화 대상 - 특이사항
// 배열의 첫 번째 요소만 사용함
// 이 API는 legacy 호환을 위해 유지됨
// 특정 상태에서만 호출 가능

// ❌ 문서화 제외 - 일반적인 설명
// 사용자 정보를 조회합니다
// 데이터를 저장합니다
```

### 2. 코드 작동 방식 특이사항

코드 분석 시 일반적이지 않은 구현 패턴을 발견하면 문서화합니다.

**문서화 대상 예시:**

- API 응답이 배열인데 현재 구현에서 0번째 인덱스만 사용
- 특정 필드가 존재하지만 현재 사용하지 않는 경우 (향후 확장용)
- 여러 상태 중 특정 상태에서만 동작하는 제약사항
- 에러 처리가 일반적이지 않은 경우 (예: 에러를 무시하고 기본값 반환)
- 하드코딩된 값이나 매직넘버

**작성 예시:**

```markdown
- `getCustomerBalances` 응답은 배열이지만 현재 구현에서 첫 번째 요소(`[0]`)만 사용
- `statusMsg` 필드는 추후 기능 확장을 위해 추가됨, 현재 미사용
- 출금 처리는 REQUESTED, FAILED, CANCELED 상태에서만 가능
- 환율 조회 실패 시 캐시된 이전 환율을 fallback으로 사용
```

문서 작성 시 아래 템플릿을 참조하세요:

- **[토픽 특이사항 템플릿](./templates/topic-template.md)**: `[topic].md` 작성 (세부 주제별 특이사항)

## 유지보수

- 코드 변경 시 **해당 특이사항도 함께 검토**
- 해결된 이슈는 문서에서 **제거** (과거 문서 유지 금지)
- 새로운 특이사항 발견 시 **즉시 기록**
