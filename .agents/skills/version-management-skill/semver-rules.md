# Semver 판단 규칙

변경 유형별로 major / minor / patch를 어떻게 매핑하는지 정리합니다.

## 변경 유형별 매핑

| 변경 유형                   | Bump  | 설명                                                         |
| --------------------------- | ----- | ------------------------------------------------------------ |
| 새 기능 추가 (하위 호환)    | minor | 새 컴포넌트, 새 API 필드(선택), 새 옵션, 새 페이지/라우트 등 |
| 버그 수정                   | patch | 기존 동작이 잘못된 것을 고침                                 |
| 문서/주석/타이포 수정       | patch | 사용자 동작에 영향 없음                                      |
| 내부 리팩터링 (동작 불변)   | patch | 구현만 바꾸고 공개 API·동작 동일                             |
| 공개 API 제거/이름 변경     | major | props 제거, 함수 시그니처 변경, 응답 스키마 호환 깨짐        |
| 기본값/동작 변경 (breaking) | major | 기존 사용처가 깨질 수 있는 변경                              |
| 보안 패치 (동작 호환 유지)  | patch | 취약점만 수정                                                |
| 보안 이슈 (노출/breaking)   | major | 노출이 있거나 동작 변경이 필요한 경우                        |

## 앱 vs 패키지

- **앱** (agreement, dashboard 등): “공개”는 해당 앱의 사용자에게 보이는 화면·동작 기준. 내부 API 변경만 있고 화면/동작이 같으면 patch 가능.
- **패키지** (moin-design-system): “공개 API”는 export된 컴포넌트·함수·타입. 이게 깨지면 major.

## moin-design-system breaking 시

- **moin-design-system**: breaking이면 해당 패키지는 **major** bump.
- **사용 앱**: MDS 버전만 올리는 경우, 앱 쪽에서 동작이 바뀌지 않으면 앱은 **patch** 또는 **minor**(필요 시)만 해도 됨. 앱에서 breaking에 맞춰 수정한 내용을 사용자에게 보여주는 변경이면 앱도 minor/major 판단.
