# 프로젝트 계획 생성 커맨드

사용자의 요청을 분석하여 프로젝트 루트의 `tmp/blueprints/YYYY-MM-DD/` 디렉토리에 계획 파일을 생성하고, 파일 기반으로 대화합니다.

## 핵심 원칙

**1. `.md` 파일이 대화의 중심이다.**

- 질문이 있으면 파일에 작성
- 사용자가 파일에서 답변
- 질문/답변 → `## 결정 사항`으로 변환하여 맥락 보존

**2. 애매하면 질문부터.** LLM이 자신있게 구현할 수 있는 수준이 아니면, 실행 전에 `.md` 파일에 질문을 작성한다. 명확하지 않은 요청에 대해 광범위한 코드베이스 탐색을 하지 말고, 더 정확한 프롬프트를 유도한다.

**3. 탐색 전 확인.** AGENTS.md의 "탐색 & 계획" 원칙을 따른다.

**4. Step은 스킬 단위로 나눈다.**

**5. 생성/수정할 파일은 스킬이 결정한다.** 절차는 Step 3 "작성 절차" 3~5번 참조.

**6. 계획 파일은 자기완결적이어야 한다.** 아래 "기록 vs 참조 원칙" 참조.

## 실행 플로우

### 1. 파일 확인 및 재개 판단

- 기존 계획 디렉토리가 있는지 확인 (`tmp/blueprints/` 디렉토리)
- **기존 디렉토리가 있으면**: `plan.md`와 `execution.md`를 읽고 상태를 파싱하여 재개 지점을 결정
  - `plan.md`에 `## 질문` 섹션이 있고 답변이 채워져 있으면 → Step 3으로 진행 (답변 기반 계획 작성)
  - `plan.md`에 `## 질문` 섹션이 있고 답변이 비어 있으면 → 사용자에게 답변 요청하고 대기
  - `execution.md`의 `## 진행 상황`의 Step 체크박스를 파싱: `[x]` 완료 건너뜀, `[~]` 진행중이면 해당 Step부터 재개
    - `[~]` Step 내부의 세부 작업 체크박스를 확인: `[x]`인 세부 작업은 건너뛰고, `[ ]`인 작업부터 이어서 실행
  - 모든 Step이 `[ ]`이면 처음부터 시작
- **없으면**: 새 디렉토리 생성

### 2. 명확성 검증 및 질문

계획을 작성하기 전에 다음이 명확한지 확인:

- **목표**: 최종적으로 뭘 만들려는 건지?
- **범위**: 어디까지 구현할 건지?
- **제약조건**: 기술 스택, 기존 코드 호환성 등
- **우선순위**: 여러 단계가 있다면 뭐부터?

**불명확한 경우** → [question-template.md](./templates/question-template.md) 형식에 따라 plan.md에 `## 질문` 섹션을 추가하고, 사용자에게 파일 경로를 안내한 뒤 대기.

**명확한 경우 (또는 답변 확인 후)** → [question-template.md](./templates/question-template.md)의 결정 사항 변환 형식에 따라 `## 질문`을 `## 결정 사항`으로 변환. 그 후 Step 3으로 진행.

### 3. 계획 작성

목표·범위가 확정되면, **메인 에이전트가 직접 계획을 작성**한다. 질문/답변 과정에서 축적된 컨텍스트를 그대로 활용한다.

**작성 절차:**

1. 프로젝트의 `.Codex/skills/` 디렉토리를 재귀 탐색하여 모든 `SKILL.md`의 `name`과 `description`을 읽는다
2. 작업 내용과 각 스킬의 description을 대조하여 관련 스킬을 선별한다
3. 파일 생성·배치가 포함된 작업이면 `file-structure-skill`을 반드시 포함
4. 선별된 스킬의 본문을 읽어 파일 구조·위치·네이밍 규칙을 파악한다
5. 파악한 규칙을 기반으로 생성/수정/삭제할 파일 목록을 도출한다
6. 아래 "스킬 기반 Step 설계 규칙"에 따라 Step을 나눈다
7. 템플릿(`./templates/`)을 읽고 형식에 맞게 두 파일을 작성한다:
   - `plan.md`: [plan-template.md](./templates/plan-template.md) 형식
   - `execution.md`: [execution-template.md](./templates/execution-template.md) 형식
8. 아래 "기록 vs 참조 원칙"과 "맥락 필드 작성 가이드"에 따라 내용을 채운다

두 파일 작성이 완료되면, 다음 단계(계획 검증)로 진행한다.

### 4. 계획 검증 (서브에이전트)

계획 작성 완료 후, 서브에이전트(`subagent_type: "general-purpose"`)로 계획의 논리적 정합성과 사용자 의도 반영을 검증한다. 검증 프롬프트: [plan-validation-prompt.md](./prompts/plan-validation-prompt.md)

- **문제 발견 시**: 사용자에게 보고 → 수정 반영 → 재검증 여부 확인
- **통과 시**: 다음 단계로 진행

> 검증은 계획의 구조와 논리만 검토한다. 코드베이스 탐색이나 구현 가능성 검증은 수행하지 않는다.

### 5. 구현 실행

사용자가 "실행해"라고 하면, `execution.md`의 `## 실행 방식` 섹션에 따라 서브에이전트로 위임하여 실행한다. Step이 1개뿐인 단순 작업은 메인 에이전트가 직접 실행해도 된다.

### 6. 구현 검증 (병렬 서브에이전트)

모든 구현 Step 완료 후, `execution.md`의 `## 검증` 섹션에 따라 검증 항목별 서브에이전트를 **병렬 실행**한다.

### 7. 파일 경로 안내

생성/업데이트된 파일 경로를 사용자에게 알려줌.

## 파일 규칙

- **위치**: 항상 **git 루트 디렉토리**의 `tmp/blueprints/YYYY-MM-DD/`에 생성
- **디렉토리 구조**:
  ```
  tmp/blueprints/YYYY-MM-DD/N-내용/
  ├── plan.md          # 인간 리뷰용
  └── execution.md     # 에이전트 실행용
  ```
  - `N`은 해당 날짜 디렉토리 내 기존 디렉토리 수 기준 자동 증가 (1, 2, 3, ...)
- **디렉토리 없으면 생성**

## 스킬 기반 Step 설계 규칙

- 각 Step이 하나의 스킬 영역에 집중하도록 분리한다 (스킬 1~2개 = Step 1개)
- 하나의 Step에 참조 스킬이 3개 이상이면 Step을 더 쪼갠다
- **예외**: 같은 파일을 여러 Step에서 반복 수정해야 하면 Step을 합칠 수 있다 (단, 합친 후에도 참조 스킬 3개 미만 유지)
- 항상 프로젝트의 실제 스킬 디렉토리를 탐색하여 최신 스킬 목록 사용
- 스킬에 매핑되지 않는 작업은 `참조 스킬: 없음 (AGENTS.md 컨벤션 적용)`

## 기록 vs 참조 원칙

계획 파일은 **새 세션(컨텍스트 없음)에서도 실행 가능**해야 한다. 단, 자동 로드되는 정보까지 복사하면 컨텍스트 낭비다.

### 인라인 기록 (세션 간 유실되는 정보)

| 항목                     | 기록 위치                     | 예시                                                   |
| ------------------------ | ----------------------------- | ------------------------------------------------------ |
| 결정 사항                | plan.md `## 결정 사항`        | "인증 방식: JWT 사용"                                  |
| 대상 파일 경로           | plan.md `영향 범위`           | `apps/dashboard/src/apis/use-get-me.tsx`               |
| API 엔드포인트·응답 형태 | execution.md Step `맥락`      | `GET /api/inspections/{id}` → `InspectionResult[]`     |
| 유사 구현 참조           | execution.md Step `맥락`      | "기존 패턴: `src/apis/use-get-transaction-detail.tsx`" |
| 비즈니스 요구사항        | plan.md `## 개요` / `## 배경` | "점검 미완료 시 송금 차단"                             |

### 참조만 (새 세션에서 자동 로드)

| 항목           | 이유                          | 적을 것                                                 |
| -------------- | ----------------------------- | ------------------------------------------------------- |
| 스킬 규칙      | Step 진입 시 스킬 호출로 로드 | 스킬 이름만 (execution.md `참조 스킬: api-layer-skill`) |
| AGENTS.md 내용 | 세션 시작 시 자동 로드        | 적지 않음                                               |
| 코드 구현 상세 | 파일에 이미 존재              | 파일 경로만                                             |

### `맥락` 필드 작성 가이드

- **"새 세션에서 이 Step을 시작할 때, 탐색 없이 바로 작업할 수 있는가?"** 를 기준으로 판단
- 2~4줄로 간결하게 작성
- API 스펙은 엔드포인트 + 핵심 응답 필드만 (전체 스키마 복사 금지)
- 유사 구현은 경로만 적고 코드는 복사하지 않음

## 작업 유형별 Step 가이드

> 참고용 Step 구성 예시. 실제 Step 구성은 작업 특성에 따라 유연하게 조정한다.

### 페이지 구현

| Step | 제목                   | 주요 작업                                        |
| ---- | ---------------------- | ------------------------------------------------ |
| 1    | 파일 생성 및 기본 구조 | page.tsx 생성, 메타데이터 설정, 기본 뼈대        |
| 2    | 레이아웃 및 UI 구성    | 디자인 시스템 컴포넌트로 레이아웃, 스타일링      |
| 3    | 데이터 연동            | API 훅 확인/생성, 데이터 fetch, 로딩/에러 처리   |
| 4    | 인터랙션 구현          | 폼 핸들링, 이벤트 처리, 성공/에러 메시지, 다국어 |
| 5    | 검증 및 마무리         | 타입 체크, 엣지 케이스, 코드 정리                |

### 컴포넌트 구현

| Step | 제목          | 주요 작업                             |
| ---- | ------------- | ------------------------------------- |
| 1    | 컴포넌트 설계 | Props 타입 정의, 파일 생성, 기본 구조 |
| 2    | UI 구현       | 디자인 시스템 컴포넌트 활용, 스타일링 |
| 3    | 로직 연결     | 상태 관리, 이벤트 핸들러, 훅 분리     |

### API 연동

| Step | 제목          | 주요 작업                                       |
| ---- | ------------- | ----------------------------------------------- |
| 1    | API 확인      | API 클라이언트 확인, Request/Response 타입 파악  |
| 2    | API 훅 생성   | useQuery/useMutation 훅 생성, 에러 핸들링       |
| 3    | 컴포넌트 연동 | 훅 호출, 로딩/에러 UI, 성공 시 후속 처리        |

### 버그 수정

| Step | 제목      | 주요 작업                                      |
| ---- | --------- | ---------------------------------------------- |
| 1    | 원인 분석 | 재현 단계 확인, 관련 코드 분석, 근본 원인 특정 |
| 2    | 수정 구현 | 수정 코드 작성, 사이드 이펙트 검토             |
| 3    | 검증      | 버그 재현 불가 확인, 회귀 테스트, 빌드 확인    |
